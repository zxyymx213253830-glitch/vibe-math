## P4 Adversarial Review: `RowSubspaceNormalization.lean`

**1. Critical: `stdOrthonormalBasis` API assumption (semantic, not just naming)**
The proof uses `stdOrthonormalBasis ℂ S` where `S : Submodule ℂ F`. This object must simultaneously be an orthonormal basis for the subspace `S` *and* carry a `LinearIsometryEquiv` (via `.repr`) to `EuclideanSpace ℂ (Fin r)`. Mathlib's standard library provides `OrthonormalBasis` for inner product spaces, but submodules require the subspace to inherit the inner product structure as an inner product space in its own right. If `stdOrthonormalBasis` is a custom wrapper that bundles the subspace-to-Euclidean isometry, this is fine—but if it merely returns an indexed orthonormal set without guaranteeing the `.repr` map is a **surjective linear isometry** onto `EuclideanSpace ℂ (Fin r)`, then `W` and `N` will not have the types claimed. The proof body treats `.repr` as yielding `≃ₗᵢ[ℂ]`, which is a stronger contract than just having an orthonormal family. Verify the exact signature: it must produce a full `LinearIsometryEquiv`, not merely an isometric embedding.

**2. `ba.repr 0` coercion ambiguity**
In the line `change J.symm (WithLp.toLp 2 (ba.repr 0, ...)) = _`, the expression `ba.repr 0` applies the representation map to `0`. But `0` here must live in `Sᗮ` (the orthogonal complement). The coercion from the zero vector of `F` into the subtype `Sᗮ` is mathematically trivial but Lean-fragile: if `ba.repr` expects an element of the subtype `↥Sᗮ`, then writing `ba.repr 0` relies on Lean inferring that `0` means `(0 : Sᗮ)` rather than `(0 : F)`. This usually works via `Subtype.coe_zero`, but if `stdOrthonormalBasis` is defined on the ambient space restricted to a subset rather than on the subtype itself, this becomes a type error. Check whether `ba` lives on `↥Sᗮ` as an independent inner product space or on `F` with support in `Sᗮ`.

**3. Dimension arithmetic is stated but not justified for zero-dimensional edge cases**
The docstring explicitly includes zero-dimensional spaces. The claims `r = finrank ℂ E` and `a + r = finrank ℂ F` are correct algebraically since `finrank ℂ S = finrank ℂ E` follows from injectivity and `finrank ℂ S + finrank ℂ Sᗮ = finrank ℂ F` is the rank-nullity/orthogonal-decomposition identity. However, when `E` is zero-dimensional, `r = 0`, `Fin r` is empty, and `EuclideanSpace ℂ (Fin 0)` is the zero space. The construction of `N : E ≃ₗ[ℂ] EuclideanSpace ℂ (Fin 0)` requires `E` itself to be identified with the zero space—this works only if `LinearEquiv.ofInjective L hL` correctly produces an equivalence to a zero-dimensional codomain. No logical gap, but the `ofInjective` construction when the range is `{0}` should be verified to not require a non-degeneracy hypothesis.

**4. No actual mathematical gaps detected in the core logic**
The decomposition strategy—orthogonal decomposition of `L x` into `S` and `Sᗮ` components, mapping `S` isometrically to `Fin r`, killing the `Sᗮ` component to zero, swapping factors, and reassembling via `Sum.elim`—is structurally sound. The use of `apply S.orthogonalDecomposition.symm.injective` to verify the projection identity is correct.
