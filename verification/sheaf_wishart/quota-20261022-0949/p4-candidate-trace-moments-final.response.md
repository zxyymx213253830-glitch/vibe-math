## P4 Adversarial Review: CandidateTraceMoments.lean

**1. Missing integrability side-condition in `candidate_actual_trace_integral_transfer`**

The theorem applies `integral_map` to rewrite both sides via pushforward measures, but `integral_map` requires the integrand to be integrable (or at least quasi-integrable) with respect to the source measure. The hypothesis only assumes `hF : Continuous F`, which does not guarantee integrability of `F ∘ X` or `F ∘ Y` against the respective measures. The companion theorem `candidate_actual_trace_integrable_transfer` correctly includes an `hI` integrability assumption, but the integral equality theorem omits it entirely. Without an integrability hypothesis on `F` (e.g., boundedness, or explicit `Integrable` assumptions on both sides), the `rw [integral_map ...]` step is unsound—`integral_map` can fail or produce junk if the function is not integrable. This is a **mathematical gap**, not an API question: the statement as written claims an unconditional integral equality for arbitrary continuous `F`, which is false unless the measures have compact support or `F` has controlled growth.

**2. Implicit type coercion well-definedness in `ComplexSample` parameter**

Throughout the file, `ComplexSample (m := p+L+q) (n := p+L)` is used as a type, and `stdGaussian _` relies on implicit inference of the index type. If `ComplexSample` is defined as `Fin m → Fin n → ℂ` (or similar), this is fine. However, the underscore in `stdGaussian _` means Lean must synthesize the type from context. In `candidate_actual_trace_integrable_transfer`, the `hI` hypothesis writes `stdGaussian _` explicitly. If the typeclass resolution for the Gaussian measure on `ComplexSample` depends on `p+L+q > 0` or `p+L > 0`, these are not stated as hypotheses. Since the instructions prohibit assuming positivity of dimensions, this is a **potential gap**: if `p = L = q = 0`, the type `ComplexSample (m := 0) (n := 0)` may be degenerate and `stdGaussian` may not be defined or may trivialize, making theorems vacuously structured but possibly breaking `fun_prop` or `measurable_pi_apply` calls that expect inhabited index types.

**3. Arithmetic mismatch risk in `candidate_trace_centered_sq_integrable` proof body**

The proof uses `.sub` and `.add` on `Integrable` instances directly as if they return `Integrable` terms (i.e., `hi.sub (...)`). In Mathlib, integrability is closed under addition/subtraction, but the exact API is typically `Integrable.add` / `Integrable.sub`, not method-chained dot notation on a term. More critically, the `convert hi using 1` followed by `funext z; simp [...]; ring` attempts to close a pointwise equality between `((∑ i, z i) - T)^2` and the expanded form `(∑ i, z i)^2 - 2*T*(∑ i, z i) + T^2`. This algebraic identity is correct, but the `ring` tactic operates on semirings, and subtraction in `ℝ` requires care—`ring` works over rings, so this should succeed, but the intermediate `.sub`/`.add` chaining on `Integrable` objects is **API-fragile**: if the actual Mathlib signatures use `Integrable.sub h₁ h₂` rather than `h₁.sub h₂`, this fails. This is an API-level concern, but since I cannot verify compilation, I flag it as a concrete risk.
